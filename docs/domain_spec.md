# 카카오톡 기능 도메인 명세

# 1. 유저 및 인증 도메인 (User & Auth Domain)

- **주요 엔티티:** `USER`, `PROFILE`, `AUTH_SESSION`

### 개요 및 목적

유저의 신원 검증, 회원가입, 로그인, 세션/토큰 관리 및 유저 본인 정보와 표현 프로필의 분리 관리를 담당하는 도메인이다.

### 주요 기능 명세

- **계정 생성 및 국제 전화번호 본인 인증:**
  - 국가 코드(E.164 표준, 예: `+82 1012345678`)를 포함한 SMS 인증 기반으로 가입 진행.
  - 국가 코드를 포함하여 저장함으로써 글로벌 해외 가입자 구별 및 국제 SMS 발송 지원.
- **1인 1계정 (단일 활성 세션) 관리:**
  - 1개의 전화번호당 1개의 활성 계정만 유지하는 단일 계정 정책 적용.
  - 동일한 전화번호로 새로운 디바이스에서 인증 로그인 시, 기존 디바이스의 점유 세션은 즉시 파기 및 자동 로그아웃 처리.
  - `AUTH_SESSION.user_id`에 `UNIQUE` 제약을 걸어 유저당 세션 row가 항상 1개만 존재하도록 DB 레벨에서 강제. 신규 로그인 시 기존 row를 갱신(UPSERT)하는 것만으로 이전 세션이 자동 교체됨.
- **인증 및 권한 부여 (JWT & OAuth 2.0):**
  - JWT (Access Token & Refresh Token) 기반의 무상태(Stateless) 세션 인증 체계 구축. Refresh Token은 `AUTH_SESSION.refresh_token`에 저장(해시 저장 권장).
  - OAuth 2.0을 통한 소셜 로그인 지원. `USER.oauth_provider`(GOOGLE, KAKAO, APPLE 등), `USER.oauth_id`로 소셜 계정 연동 정보 관리.
- **다중 프로필 (멀티프로필) 관리 및 정책 제한:**
  - 1명의 유저가 기본 프로필 외에 멀티 프로필(오픈채팅용, 비즈니스용 등)을 생성 및 지정.
  - **정책 제약:** 무분별한 생성을 방지하기 위해 유저당 멀티프로필 생성을 **최대 3개**로 제한하는 검증 로직 적용.

### DB 및 아키텍처 설계 포인트

- **`USER`와 `PROFILE` 테이블의 제3정규화(3NF) 분리:**
  - **근거:** 이메일/비밀번호/전화번호 등 자주 변경되지 않는 신원 정보와 닉네임, 상태메시지, 프로필 이미지 등 자주 변경되는 표현 정보를 격리하여 수정 이상(Update Anomaly)을 원천 차단.
  - 1명의 유저는 N개의 프로필을 가질 수 있는 1:N 구조로 확장성을 확보.
- **`AUTH_SESSION` 분리:**
  - **근거:** 로그인마다 갱신되는 휘발성 세션/디바이스 정보(`device_id`, `refresh_token`)를 거의 변경되지 않는 `USER`의 신원 정보와 함께 두면 동일한 갱신 이상 문제가 발생. `USER`와 동일한 3NF 원칙에 따라 세션 상태를 별도 테이블로 분리.
  - `user_id`에 `UNIQUE` 제약을 걸어 "1인 1계정 단일 활성 세션" 정책을 DB 스키마 차원에서 강제.

# 2. 친구 도메인 (Friend Domain)

- **주요 엔티티:** `FRIEND`

### 개요 및 목적

유저 간의 관계(인맥 네트워크)를 형성하고, 주소록 동기화 및 친구 상태(활성, 차단, 숨김, 즐겨찾기)를 관리하는 도메인이다.

### 주요 기능 명세

- **주소록 자동 동기화 & 수동 검색:**
  - 모바일 기기 연락처 전송을 통한 자동 친구 추가 및 유저 고유 ID/QR 검색 추가.
- **친구 상태 및 개인화 관리:**
  - **일반 (`ACTIVE`):** 정상 친구 관계.
  - **숨김 (`HIDDEN`):** 친구 목록에서 감춤 (메시지 수신 가능).
  - **차단 (`BLOCKED`):** 메시지 수신 차단 및 프로필 비공개 처리.
  - **즐겨찾기 (`FAVORITE`):** 자주 대화하는 친구 목록 상단 고정.
  - **별칭 (`alias`):** 내가 직접 지정한 친구의 이름 저장.
  - **멀티프로필 지정 (`target_profile_id`):** 해당 친구에게만 보여줄 내 전용 프로필 설정.

### DB 및 아키텍처 설계 포인트

- **계정 간 PK 참조 및 프로필 조인(Join) 분리:**
  - **근거:** `FRIEND` 테이블은 `user_id`와 `friend_id`로 계정 대 계정의 순수한 관계만 관리. 친구 목록 조회 시 상대방의 최신 `PROFILE` 데이터를 JOIN하여 조회함으로써 데이터 일관성 보장.
- **복합 유니크 제약조건 `(user_id, friend_id)` 및 B-Tree 인덱스 최적화:**
  - **근거:** 동일 친구 중복 등록 방지. 복합 유니크 인덱스가 적용되어 "유저 A가 유저 B를 친구로 추가했는가?" 탐색 시 **O(log N)** 속도로 탐색하여 대용량 데이터에서도 초고속 조회를 보장.

# 3. 채팅 및 메시지 도메인 (Chat & Message Domain)

- **주요 엔티티:** `CHAT_ROOM`, `ROOM_PARTICIPANT`, `MESSAGE`, `MESSAGE_TEXT_CONTENT`, `FILE_METADATA`, `MESSAGE_LOG`

### 개요 및 목적

실시간 대화방 생성, WebSocket 기반 메시지 수발신, 대화 내역 저장, 안 읽은 메시지 수 연산, 답장 및 삭제를 담당하는 시스템 핵심 도메인이다.

### 주요 기능 명세

- **다양한 대화방 지원 (나와의 채팅방 포함):**
  - 1:1 대화방, 그룹 대화방, 오픈채팅방뿐만 아니라 자신만의 메모/저장소 역할을 하는 **'나와의 채팅방' (`room_type = 'MY'`)** 지원.
- **실시간 메시지 송수신:**
  - WebSocket + STOMP 프로토콜을 이용한 초저지연 양방향 실시간 메시지 전달.
- **채팅방 유저별 개인화 설정:**
  - 같은 대화방이라도 유저별로 설정이 다를 수 있도록 `ROOM_PARTICIPANT`에 개인화 필드 지원 (`custom_room_name`, `is_muted` 알림 끄기, `is_pinned` 상단 고정, `background_image_url`).
- **메시지 부가 기능:**
  - `parent_message_id` 자가 참조 연관관계를 통한 답장(Reply), 파일/이미지 첨부, Soft Delete (메시지 삭제 처리).
  - `message_type`에 `GIFT` 추가 — 커머스 도메인의 선물하기 결제 완료 시 발송되는 선물 카드 메시지 지원 (7. 커머스/선물하기 도메인 참고).
- **메시지 변경 이력 감사(Audit) 로그:**
  - `MESSAGE_LOG`에 메시지의 생성/수정/삭제(`action_type`: `CREATE`, `UPDATE`, `DELETE`) 이력과 당시 원본 내용(`raw_content`)을 별도 적재하여 분쟁 대응 및 감사 추적 지원.

### DB 및 아키텍처 설계 포인트

- **`MESSAGE`와 `MESSAGE_TEXT_CONTENT` 수직 분할 (1:1 Vertical Partitioning):**
  - **근거:** 대화방 스크롤 페이징 조회 시 무거운 `content` (TEXT 타입)를 읽지 않고 가벼운 메타데이터만 스캔하여 디스크 Read I/O 병목을 대폭 감소.
- **`last_read_message_id` 기반 인덱스 스캔 안 읽은 카운팅:**
  - **근거:** `ROOM_PARTICIPANT`에 `last_read_message_id`를 기록해 두고, `WHERE room_id = :roomId AND id > :lastReadMessageId` 쿼리를 실행. `(room_id, id DESC)` 복합 인덱스를 타고 해당 범위만 고속 스캔하여 정확한 안 읽은 메시지 수 연산.

# 4. 이모티콘 도메인 (Emoticon Domain)

- **주요 엔티티:** `EMOJI`, `USER_EMOJI`, `EMOJI_METADATA`, `USER_SUBSCRIPTION`

### 개요 및 목적

채팅 내 풍부한 감정 표현을 위한 이모티콘 메타데이터 관리, 유저별 보유함, 메시지 내 이모티콘 매핑 및 구독 상품을 지원하는 도메인이다.

### 주요 기능 명세

- **이모티콘 카탈로그 및 보유함:**
  - 팩/카테고리별 정적·동적 이모티콘 관리 및 유저가 구매/선물받은 이모티콘 보유함 관리.
- **이모티콘 플러스 (구독형 서비스) 권한 로직:**
  - 구독형 상품 유저를 위해 `USER_SUBSCRIPTION`에 구독 상태 (`is_emoticon_plus_active`, `expired_at`)를 관리. `user_id`에 `UNIQUE` 제약을 걸어 유저당 구독 레코드가 항상 1개만 존재하도록 강제.
  - 구독 활성화 상태 유저의 경우, 개별 구매 여부와 상관없이 구독 대상 이모티콘 카탈로그 전체에 대해 서비스 레이어에서 사용 권한 승인.

### DB 및 아키텍처 설계 포인트

- **N:M 관계 해소 및 메시지 테이블 용량 최적화:**
  - **근거:** 메시지 발송 시 긴 이미지 URL을 메인 메시지 테이블에 저장하지 않고 `emoji_id` 매핑만 생성하여 DB 용량을 대폭 절약.

# 5. 알림 도메인 (Notification Domain)

- **주요 엔티티/컴포넌트:** `NOTIFICATION_SETTING`, `DEVICE_TOKEN`, Message Queue (Kafka/RabbitMQ)

### 개요 및 목적

앱 비활성화 상태이거나 미접속 중인 유저에게 신규 메시지 및 이벤트를 모바일 푸시 알림(FCM / APNs)으로 전달하는 도메인이다.

### 주요 기능 명세

- **푸시 알림 발송 및 토큰 관리:**
  - FCM(Android) / APNs(iOS) 연동 및 기기별 토큰 갱신/삭제.
- **알림 방해금지 시간대 설정:**
  - 매일 반복되는 방해금지 시간대를 위해 `quiet_start_time`, `quiet_end_time`을 `TIME` 타입 (예: `22:00:00`)으로 정밀 관리.

### DB 및 아키텍처 설계 포인트

- **Message Queue (Kafka / RabbitMQ) 기반 비동기 이벤트 버퍼 아키텍처:**
  - **근거 (장애 격리):** 메시지 전송과 외부 푸시 알림 발송을 동기(Synchronous)로 처리할 경우, FCM/APNs 외부 서버 장애나 지연 발생 시 핵심 채팅 메시지 발송까지 지연/중단됨.
  - **개선:** 메시지 생성 이벤트를 Message Queue로 발행(Publish)하고 즉시 응답을 반환. 알림 전용 서버가 큐의 이벤트를 비동기로 소비(Consume)하여 발송함으로써 **채팅 서비스의 SLA 및 안정성을 100% 보장.**

# 6. 보이스톡 / 페이스톡 도메인 (Call / RTC Domain)

- **주요 엔티티/컴포넌트:** `CALL_LOG`, WebRTC Signaling Server

### 개요 및 목적

유저 간 1:1 또는 그룹으로 진행되는 실시간 음성(보이스톡) 및 영상(페이스톡) 통화 신호 제어와 통화 이력을 관리하는 도메인이다.

### 주요 기능 명세

- **WebRTC 기반 1:1 / 그룹 통화 시그널링:**
  - 통화 요청, 수신, 거절, 부재중 처리 및 P2P 직접 연결을 위한 통화 신호 중계.
- **통화 세션 제어:**
  - 통화 중 음소거, 비디오 On/Off, 세션 연결 상태 변경 처리.
- **통화 이력 적재:**
  - 통화 종료 후 대화방 타임라인에 통화 결과 메시지 발송 및 `CALL_LOG` 적재.

### DB 및 아키텍처 설계 포인트

- **WebRTC Signaling Server 분리 및 메타데이터 기반 기록:**
  - **근거 (P2P 통화):** 대용량 미디어(음성/영상) 스트림은 DB나 웹서버를 거치지 않고 피어 간(P2P) 직접 전달. 시그널링 서버는 연결 중개만 담당하며, DB에는 통화 종료 시 '통화 시간, 수발신자, 통화 상태' 메타데이터만 `CALL_LOG`에 가볍게 저장.

# 7. 커머스 / 선물하기 도메인 (Gift & Commerce Domain)

- **주요 엔티티/컴포넌트:** `GIFT_PRODUCT`, `GIFT_ORDER`, `VOUCHER`, `GIFT_METADATA`

### 개요 및 목적

채팅방 내에서 친구에게 상품 및 기프티콘을 구매하여 전달하고, 모바일 교환권을 생성·사용하는 커머스 연동 도메인이다.

### 주요 기능 명세

- **상품 카탈로그 및 PG 결제 연동:**
  - 선물하기 상품 목록 조회 및 외부 PG사 결제 연동.
- **선물 메시지 카드 발송:**
  - 결제 완결 시 지정 대화방으로 선물 카드 메시지 (`message_type = 'GIFT'`) 자동 전송.
  - `GIFT_METADATA`가 해당 `MESSAGE`와 결제 성공으로 발급된 `VOUCHER`를 연결(둘 다 `UNIQUE` 제약으로 1:1 매핑 강제)하여, 채팅방에서 선물 카드 메시지를 열람하면 정확히 어떤 교환권인지 조회 가능.
- **교환권 (Voucher) 라이프사이클 관리:**
  - 수신된 바코드 교환권 조회, 사용 완료 처리 (`USED`), 유효기간 연장 및 환불.

### DB 및 아키텍처 설계 포인트

- **RDBMS 기반의 엄격한 트랜잭션 (ACID) 보장 및 커머스-채팅 연동:**
  - **근거:** 재고 차감 및 결제 처리는 강한 정합성(Strong Consistency)이 필수이므로 RDB 트랜잭션 범위 내에서 관리. 결제 성공 시 `VOUCHER`를 생성하고 `GIFT_METADATA`로 `MESSAGE`와 연결하여 채팅 타임라인과 커머스 간 정합성을 완전 보장.
- **`GIFT_METADATA` 위성(satellite) 테이블 분리:**
  - **근거:** `voucher_id`를 `MESSAGE`에 직접 컬럼으로 추가하면 GIFT 타입이 아닌 대다수의 메시지 행에서 해당 컬럼이 NULL로 낭비됨. `EMOJI_METADATA`/`FILE_METADATA`와 동일하게, GIFT 메시지에 대해서만 별도 테이블에 행을 생성하는 패턴으로 저장 공간 낭비를 방지.
